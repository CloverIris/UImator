# UImator 架构总览

- 版本：v0.1（决策阶段）
- 日期：2026-10-26
- 状态：待评审

## 1. 这份文档解决什么

UImator 的功能清单很长（捕获、拆解、3D 舞台、相机、时间轴、节拍、排版、导出）。但真正会让人返工的只有三条路线：**怎么把页面变成素材**、**用什么渲染舞台**、**怎么把帧变成视频**。这三条一旦选错，后面所有功能都是沉没成本。

本文只做三件事：定义系统边界、列出模块与数据流、给出可量化的预算与开放问题。具体的取舍理由在 `adr/` 目录，一条决策一个文件。

## 2. 目标与非目标

**目标**

- 输入一个 URL 或本地端口，把页面拆成可独立摆布的图层，进入 3D 舞台。
- 用「状态 → 状态」的方式编排镜头与舞台，而不是逐属性 K 帧。
- 导出 1080p / 4K、24/30/60fps 的 MP4，帧级确定、可重复。
- 第一次出片（720p 预览）在输入 URL 后 30 秒内完成。

**非目标（v1 明确不做）**

- 不做实时交互演示（那是 Arcade / Navattic 的地盘）。
- 不做可编辑 DOM / SVG 矢量化（见 ADR-0002 的取舍）。
- 不做节点图编辑器（见 ADR-0005）。
- 不做批量抓取 / 竞品批量解构（法务与风控，见 ADR-0010）。
- 不做浏览器插件版、不做纯 Web 版。

## 3. 系统全景

```
┌──────────────────────────────────────────────────────────────────────────┐
│ Electron Main（受信）                                                     │
│                                                                          │
│  Session A（partition: capture，隔离）                                    │
│    WebContentsView ── 目标站点（不可信，sandbox，无 Node）                  │
│      └─ CDP：Emulation / Page.captureScreenshot / Input / Runtime         │
│                                                                          │
│  Session B（partition: stage，隔离）                                      │
│    隐藏窗口 ── 导出专用舞台（同一套 three.js 场景，离屏运行）               │
│                                                                          │
│  Asset Store（content-addressed，落盘）                                   │
│  IPC 网关（只传结构化消息 + content hash，不传裸 DOM）                      │
├──────────────────────────────────────────────────────────────────────────┤
│ Editor Renderer（受信，绝不加载远程内容）                                  │
│    素材箱 │ 3D 视口（three.js）│ 检查器 │ 时间轴 │ 排版 │ 音频              │
├──────────────────────────────────────────────────────────────────────────┤
│ Export Worker（独立进程）                                                  │
│    固定步长循环 → 场景求值 → 渲染 → 子帧累积 → VideoEncoder → mp4-muxer     │
└──────────────────────────────────────────────────────────────────────────┘
```

关键隔离：**目标站点、编辑器、导出器是三个不同的进程 + 三套 session**。目标站点永远拿不到 `fs`、拿不到我们的 IPC，也永远不进入编辑器进程。

## 4. 三条不变量

### I1 素材是缓存，不是真相

工程文件里对每个素材存的是「重截配方」：

```jsonc
{
  "sourceId": "src_01",
  "route": "https://app.example.com/dashboard",
  "viewport": { "w": 1440, "h": 900 },
  "deviceScaleFactor": 3,
  "clip": { "x": 312, "y": 96, "w": 420, "h": 280 },   // CSS px
  "state": { "scrollY": 0, "hover": null, "timeOffset": 1200, "demoData": "seed_42" },
  "matcher": { "selectorPath": "...", "textDigest": "9f2c", "role": "card" }
}
```

纹理只是这份配方的产物，按内容哈希存放在磁盘缓存里。带来的好处：

- 导出 4K 时按镜头需要重截更高倍率，不必重新拆一遍页面。
- 页面改版后能检测到配方失效（matcher 命中失败 / 图像的感知哈希漂移），提示用户而不是静默出一堆旧图。
- 工程文件可以很小（分享时只带配方 + 1x 预览纹理）。

### I2 舞台上只有一个 canvas

所有 UI 图层都是带纹理的网格，所有文字要么是 MSDF 字形，要么是纹理。没有 `CSS3DRenderer`，没有叠在 canvas 上的 DOM 文本。

这条约束同时买到三样东西：统一的后期（辉光 / 景深 / 颗粒 / 色差 / 运动模糊）、正确的深度遮挡、以及在**窗口尺寸之外**渲染的能力（超采样与 4K）。

### I3 任意一帧 = `f(project, t)`

渲染一帧不允许读墙钟、不允许用未播种的 `Math.random()`、不允许在帧中途 await 纹理加载。

这条约束是导出可重复、可断点续渲、可并行分块的前提。它的代价是粒子、闪烁、随机几何这些效果必须写成「帧号 → 伪随机序列」的形式（`mulberry32(seed ^ frameIndex)`），而不是随手 `Math.random()`。

## 5. 模块与边界

| 模块 | 职责 | 明确不做 |
| --- | --- | --- |
| `capture-core` | 驱动 CDP、等待稳定、裁剪截图、抓状态 | 不解析语义、不判重 |
| `capture-planner` | 遍历 DOM、聚类候选、打分、生成配方 | 不做「理解」，只做候选生成 |
| `asset-store` | 内容寻址、LOD 分级、失效检测 | 不持有场景数据 |
| `scene-graph` | 图层、深度策略、相机、灯光、背景 | 不含时间信息 |
| `timeline` | 状态节点、过渡段、轨道、求值 `f(t)` | 不直接碰 three.js |
| `renderer` | three.js 渲染、材质、后期 | 不做时间推进 |
| `typography` | 字体解析、MSDF 生成、排版、文字动画 | 不负责 UI 文案生成 |
| `audio-beat` | BPM / 节拍 / 小节线 / 磁吸 | 不做混音 |
| `exporter` | 固定步长、编码、封装、断点 | 不改场景 |
| `project-io` | 打包、版本、迁移 | — |
| `ui` | 素材箱、视口、检查器、时间轴 | — |

渲染层与时间层分离是刻意的：`timeline` 输出一个纯数据快照（每个图层的位置/旋转/透明度/材质参数），`renderer` 只负责把快照画出来。这样导出时可以在无 UI 的进程里跑同一套求值逻辑。

## 6. 三条数据流

**捕获流**：加载 URL → 等稳定（字体、首屏动画、网络静默）→ DOM 遍历聚类 → 用户点选 / 确认候选 → 逐素材 CDP 截图（含 hover 态与动画相位）→ 提取品牌 token → 写入 asset store + 配方。

**编排流**：素材入箱 → 自动生成初稿（模板 + 种子）→ 用户调整状态节点 / 相机 / 排版 → 求值器实时预览（1–2x 贴图，60fps）。

**导出流**：扫描时间轴得到所有镜头区间 → 算出每个素材的最大屏幕像素 → **回到源页面按需重截（第二遍）** → 烤 LOD 纹理 → 固定步长逐帧渲染 → 子帧累积 → 编码 → 封装。

## 7. 性能与容量预算

这些数字不是承诺，是**待尖峰验证的假设**。任何一项超标都要回到 ADR 重新选型。

| 项 | 预算 | 说明 |
| --- | --- | --- |
| 单工程素材数 | ≤ 120 | 超过就开始分镜 |
| 同屏可见图层 | ≤ 60 | 曲面墙用实例化 + 图集 |
| 纹理显存 | ≤ 1.5 GB | 只保留可见 mip，离屏即释放 |
| 编辑器预览 | 1080p / 60fps | 1–2x 贴图，无累积模糊 |
| 导出 1080p60 | ≤ 120 ms/帧 | 30 秒片 ≈ 3.6 分钟 |
| 导出 4K60 | ≤ 500 ms/帧 | 30 秒片 ≈ 15 分钟；开 4x 累积则 ×3.5 |
| 首次出片延迟 | ≤ 30 s | 720p 草稿，不含 4K 渲染 |
| 抓取单页 | ≤ 15 s | 含字体与首屏动画等待 |

## 9. 开放问题（必须由尖峰回答）

1. `deviceScaleFactor` 提到 4 以上时，Chromium 截图在长页面上是否稳定？单张纹理上限在哪？
2. 隐藏窗口里跑 WebGL + WebCodecs，吞吐是否接近可见窗口？（离屏合成的老问题）
3. 中文 MSDF 在 4K 特写下，和直接光栅化比，观感差多少？子集化后图集规模多大？
4. 分层平面做景深时，透明边缘的散景是否会出现「剪纸感」？需要多少层才不穿帮？
5. 同一份工程在两个 GPU（ANGLE/Metal vs D3D）上渲染，像素差异有多大？能否用感知哈希做回归？
6. 可见窗口加载站点时，Cloudflare 类风控的通过率如何？是否会被判定为自动化？
7. 两遍重截中，第二遍回到源页面时，页面已变化（A/B 实验、实时数据）导致素材对不上，如何优雅降级？
