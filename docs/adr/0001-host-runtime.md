# ADR-0001 宿主运行时：Electron

- 状态：已接受
- 日期：2026-10-26
- 关联：ADR-0002、ADR-0008

## 背景

UImator 要做的第一件事，是**在用户机器上真实打开一个第三方网页，并精确截取其中任意一块**。这件事对运行时有三个硬要求：

1. 能加载任意站点（登录态、cookie、CORS 图片、WebGL、iframe）。
2. 能拿到合成器级别的截图（不是 `canvas.toDataURL`，不受跨域污染影响）。
3. 能在窗口之外、以任意分辨率渲染（4K 导出、超采样）。

## 决策驱动

- 捕获精度与可控性（最高优先级）
- 三端表现一致（模板效果不能因平台而异）
- 导出能力（WebCodecs / 离屏渲染 / 原生 ffmpeg 兜底）
- 分发与签名成本
- 长期维护成本（Chromium 安全更新节奏）

## 备选方案

### A. Electron（选定）

- 自带完整 Chromium，**CDP 全量可用**，各平台同一版本、同一渲染结果。
- `WebContentsView` 把目标站点嵌进应用；`session` 分区天然隔离登录态。
- `Page.captureScreenshot` 精确裁剪、支持 `captureBeyondViewport`、无视跨域污染。
- WebCodecs / WebGPU / WebGL2 齐全；可另开隐藏窗口做离屏导出。
- 可访问系统字体目录、可调原生 ffmpeg。

代价：安装包 ~150–250 MB；需要跟 Chromium 安全更新；macOS 需公证、Windows 需签名。

### B. Tauri

- 包体小 10 倍，但 macOS 走 **WKWebView**、Linux 走 **WebKitGTK**，**两者都没有 CDP**，只有 Windows 的 WebView2 有。
- 三个渲染引擎的亚像素、字体、混合模式、WebGL 实现各不相同，**模板效果无法保证一致**，导出结果也不可复现。
- 无 `Page.captureScreenshot` 这条稳定路径，捕获只能退回 `html-to-image` 这类 DOM 序列化（见 ADR-0002 已否决）。

结论：**不可用**。这不是体积问题，是能力缺失。

### C. 纯 Web 应用 + 用户浏览器

- 无法跨域加载第三方站点，无法截图，无法 4K 渲染，无法读本地字体，无法导出大文件。
- 结论：不可用。

### D. 浏览器扩展

- 分发受商店审核；无法稳定拿 4K 截图；无法在窗口外渲染；无法做导出管线；CSP 与 MV3 生命周期限制多。
- 结论：可作为未来「采集端」的补充，不能作为宿主。

### E. 自带 CEF / Chromium 嵌入式框架

- 能力上等价于 Electron，但构建与跨平台分发成本高一个量级，没有生态（自动更新、公证、崩溃上报都要自己写）。
- 结论：等 Electron 真的挡住路再说。

## 决策

采用 **Electron**，并锁定一个 Chromium 大版本。工程文件里记录 `electronVersion` 与 `chromeVersion`，因为**截图与字体渲染在版本间会有细微差异**，跨版本打开旧工程时要提示。

## 理由

唯一同时满足「加载任意站点 + 合成器截图 + 窗口外渲染 + 三端一致」四个条件的方案。其余方案都在其中至少一项上失效。

## 后果

**正面**

- 捕获与渲染共用一套 Chromium，所见即所得。
- 导出可以在同一进程模型里做，不需要外部渲染农场。
- 生态成熟：自动更新、崩溃上报、公证流程都有现成方案。

**负面**

- 包体大、冷启动慢，需要认真做首屏。
- 每年至少一次 Chromium 大版本升级，每次都要跑视觉回归（见 ADR-0007 的哈希回归）。
- 内存开销高，目标站点的内存泄漏会传导到整个应用，必须给捕获 session 设内存上限并定期销毁视图。

## 何时重审

- 若 Electron 的截图 API 在某个版本出现无法绕过的回归；
- 若需要 WebGPU 的某个特性而 Electron 滞后超过两个版本；
- 若包体成为转化的主要障碍（可从「下载版 + 云端渲染」两条产品线拆开解决）。
