# ADR-0013 语义树：动画按「信息结构」寻址，不按截图坐标

- 状态：已接受（已实现 `--tree`，待接入场景图）
- 日期：2026-10-26
- 关联：ADR-0004、ADR-0012

## 背景

ADR-0012 解决了「一块 UI 能不能拆开」：拆成带 alpha 的层，再合回去无损。但那只回答了**渲染**问题，没有回答**寻址**问题。

如果产物只是「一堆坐标已知的图」，那么动画只能写成「把第 7 张图往上移 40px」——换一个站点就全废，模板无法复用，所谓「一键出片」不成立。

真正需要的是：**每个可动画的单元都有语义、有角色、有文本、有层级，并且能被稳定地查询到。**

## 决策

捕获产物是 `UINode` 树，不是图片列表。每个节点同时携带四类信息：

| 类别 | 字段 | 用途 |
| --- | --- | --- |
| 身份 | `id` / `path` / `depth` / `parent` | 稳定寻址、撤销重做、增量更新 |
| 语义 | `role` / `tag` / `text.value` | 模板匹配（「所有 heading 依次入场」） |
| 几何 | `box`（相对父）/ `abs`（文档绝对） | 3D 摆放、动画插值、命中测试 |
| 表现 | `style`（圆角/背景/字色/字号/字重/边框）/ `render`（贴图 + dpr） | 重建外观、重新打光 |
| 可动画 | `animatable[]` + `text.glyphs[]` | 程序动画的属性白名单与字级几何 |

`render` 是**载荷**，`role` 与 `text` 是**接口**。前者让画面正确，后者让动画可编程。

## 寻址：三级选择器

动画绑定不写死节点 id，而是写查询：

```jsonc
{ "target": "role:card",              "stagger": 60 }   // 所有卡片，依次入场
{ "target": "role:heading",           "prop": "textReveal" }  // 所有标题，逐字浮现
{ "target": "text~'免费开始'",         "prop": "translateZ" }  // 按文案定位按钮
{ "target": "path:.tier.featured > role:button", "prop": "hoverState" }
```

- `role:*` —— 跨站点复用模板的基础
- `text~` —— 文案是产品里最稳定的锚点之一（比 class 稳）
- `path:` —— 需要精确定位时的兜底

这三级的优先级是刻意的：**模板只允许依赖 role 与 text，path 只用于用户手工微调**。否则模板立刻退化成「只能用于某个特定网站」。

## 实测（`npm run tree`，目标 `#features`）

```
group   div.wrap
  group   div.sechead
    heading h2  315×51  「为增长团队造的仪表盘」
    text    p   154×22  「开箱即用 · 无需数据工程」
  group   div.grid
    card  article.feature-card  360×181
      card    div.ic  38×38
      heading h3  310×26  「实时指标」
      text    p   310×43  「秒级延迟的事件流…」
    …×6
```

29 个节点（12 card / 7 heading / 7 text / 3 group），按树序把每张载荷贴回原位：

- 与原图平均差 **0.71 / 255**
- 差异 > 16 的像素 **1.18%**（集中在文字抗锯齿边缘）
- 3 个 `group` 的载荷为空 —— 它们是**纯结构节点**，只承担变换与分组，不承担绘制

这条「group 可以没有图」的性质很重要：它说明树的节点 ≠ 图片，树是骨架，图只是挂在上面的皮。

## 后果

**正面**

- 动画编排可以完全脱离坐标：模板写一次，跑在任何被捕获的站点上。
- 逐字动画有几何依据（`glyphs`），不需要重建排版。
- 节点 id 稳定，可做增量重截、diff、局部替换。

**负面**

- 树的质量决定一切：`role` 判错（比如把图标判成卡片）会让模板错位，而且用户很难解释为什么。
- 节点数膨胀：一个首屏 25–40 个节点，比「一张图」多一个量级的贴图管理成本。
- 语义来自启发式规则，不是真值。同一个组件在不同站点可能被判成不同 role。

## 已知缺口（下一轮补）

1. `style` 里缺 `fontFamily`、`letterSpacing`、`lineHeight` —— 这三样是重新排版（MSDF 路径）必需的。
2. 没有状态：`:hover` / `:active` / `:focus` 尚未作为节点的「变体」存下来。
3. 图标的 SVG 路径没有抽出，仍是位图（放大到 6x 以上会软）。
4. `z-index` / 层叠上下文只体现在树序，没有显式层级，3D 里做深度排序可能不够。
5. 输入框的 `value` / `placeholder` 没有单独成字段。

## 何时重审

- 若 `role:card` 在真实站点上的误判率超过 20%，说明纯几何规则到头了，需要引入视觉模型或组件树（React DevTools hook）。
- 若模板作者 80% 的时间在写 `path:`，说明 role 体系不够用，需要扩角色而不是让用户兜底。
